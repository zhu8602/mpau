## 0. 一句话定位

`mpau` = **本地部署的「电商内容多平台批量发布」工具**：
浏览器自动化（patchright）把一条视频分发到 8~10 个内容/电商平台，配 **AI 文案引擎 + 批次审阅队列 + 风控限速 + 防重发**，外面套一层 Flask + Vue 3 的 Web 管理后台，同时保留 CLI 与 Agent Skill 双入口。

- 目标用户：电商卖家 / 矩阵工作室 / 代运营（见 `docs/commercial-plan.zh-CN.md`）
- 真实业务样本（本机数据）：椰蓉面包带货视频，抖音 `douyin1`(冰绮z) + 快手 `kuaishou1` 批量分发，DeepSeek 生成差异化文案

## 1. 分层架构

```text
┌──────────────────────────────────────────────────────────────┐
│ 入口层                                                        │
│  Web UI (Vue3 SPA, web/ui/dist)   CLI (mpau_cli.py)   Skills  │
└───────────────┬──────────────────────────┬───────────────────┘
                │ HTTP /api/*              │ mpau <platform> <action>
┌───────────────▼──────────────────────────▼───────────────────┐
│ 服务层  web/app.py (Flask, 默认 127.0.0.1:8898, 令牌认证)      │
│  任务队列(内存 dict + RLock) ── spawn 子进程 ── 逐行日志流式回传 │
└───────────────┬──────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────┐
│ 编排层  pipeline/  (Web 与 CLI 共用, 无 Web 依赖)              │
│  store( SQLite ) · planner(平台能力/命令构建) · copy_engine(AI) │
│  scanner(扫描/CSV) · batch_runner(批次状态机) · scheduler(限速) │
│  rules(文案校验) · account_meta(昵称) · config                 │
└───────────────┬──────────────────────────────────────────────┘
                │ 子进程调用：mpau <platform> upload-video ...
┌───────────────▼──────────────────────────────────────────────┐
│ 执行层  uploader/<platform>_uploader/main.py                   │
│  patchright(async) + stealth.min.js + storage_state(cookie JSON)│
└──────────────────────────────────────────────────────────────┘
```

> ⚠️ 勘误：本项目**不使用 persistent context**——全仓 `launch_persistent_context` / `user_data_dir` **0 命中**（已 grep 验证）。实际模式是每次都 `browser.new_context(storage_state=cookie.json)` 开临时上下文，结束时 `context.storage_state(path=...)` 回写；`utils/ui_window.py` 的 `ui-profile` 只服务于 Web 界面的 --app 窗口，与发布无关。**反检测全部内容 = 注入一次 `utils/stealth.min.js`**（`utils/base_social_media.py:21-24`），无指纹随机化、无代理轮换。

**关键设计点**：Web 与 CLI **不共享内存**，Web 通过 `runner.spawn_mpau()` 拉起 `mpau` 子进程执行发布；批次调度状态落 SQLite，因此进程重启后可恢复（`running` → `已中断`，可重新批准续传）。

## 3. 后端 `web/app.py`

### 3.1 启动与认证
- 端口 `MPAU_WEB_PORT`（默认 8898），绑定 `MPAU_WEB_HOST`（默认 127.0.0.1，设 `0.0.0.0` 为局域网模式，仍需令牌）。
- 令牌：`MPAU_WEB_TOKEN` env > `data/web_token.txt`（不存在则 `secrets.token_urlsafe(24)` 生成）。
- `@app.before_request require_auth()`：除 `/login`、`/manual` 外全部拦截。
  - 三条携带方式：`http://host:8898/?token=XXX`（种 `mpau_token` Cookie 后 302）、`Authorization: Bearer`、`X-MPAU-Token` 头。
  - `secrets.compare_digest` 恒定时间比较；Cookie 认证的**写操作**校验 `Sec-Fetch-Site` 同源（防 CSRF），跨站返回 403。
- SPA 托管：`ui/dist` 存在则 `GET /` 托管新 SPA + 前端路由 fallback，否则回退 `templates/index.html`；`/legacy` 永远指旧版。
- `/manual` → `docs/使用手册.html`（顶栏「使用手册」入口）。

### 3.2 任务队列
- 内存 `_tasks: dict[str, dict]` + `threading.RLock`（可重入，支持回调内嵌套加锁），同时落 SQLite `tasks` 表。
- 执行模型：后台线程 → `runner.spawn_mpau(cmd)` 子进程 → `runner.stream_mpau` 逐行回调 `append_log`（内存 + `store.append_task_log`，上限 600 行）。
- 状态：`queued / running / success / failed / canceled / interrupted`；重启时 `running` → `interrupted`。
- 前端约定标记（日志内出现即触发 UI 提示）：`[VERIFY_REQUIRED]`（短信验证码，`POST /api/verify` 回填）、`[MANUAL_ACTION]`。

## 5. 数据模型（`data/mpau.db`，`store.init_db()` 幂等建表 + ALTER 迁移）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `tasks` | id/kind/platform/account/label/cmd/status/error/exit/created/started/finished/log | `cmd` 为列表时 join 成串；日志落库支持重启后回看 |
| `videos` | id/path(UNIQUE)/sha256/size/base_title/base_desc/base_tags/goods_json/schedule/cover/status | 扫描即算 sha256（分块 1MB） |
| `items` | id/batch_id/video_id/platform/account/title/desc/tags/candidates_json/schedule/goods_json/status/task_id/retry/error/created/updated/published_at | 一条 = 视频 × 平台 × 账号 |
| `batches` | batch_id/brief/created/video_ids | `video_ids` 为旧库 ALTER 补列 |
| `published` | (sha256, platform, account) PK + published_at | **防重发**唯一键 |
| `settings` | key/value | LLM 与风控配置（JSON），与 `data/config.json` 并存 |

`items.status` 状态机：
```text
draft ──批准──▶ approved ──调度──▶ running ──┬─▶ success
  ▲                ▲                          ├─▶ failed ──重试──▶ approved
  │                │                          ├─▶ skipped(配额/防重发)
  └──重新生成───────┘                          └─▶ interrupted(进程重启)
needs_manual(未选账号 / AI 生成失败 / 缺必填字段)
```

## 6. 核心业务流（一条视频 → N 平台）

1. **入料**：`POST /api/batch/scan`（扫文件夹）/ `import`（CSV，每视频一行）/ `videos/add`（单条，无批次自动新建，重复返回 `added:false`）→ `videos` 表 + `batches.video_ids`。
2. **文案**：`POST /api/batch/plan` 用 `planner.expand_items` 把 视频 × 平台 × 账号 展开成条目 → `POST /api/batch/generate` 逐平台调 LLM（`copy_engine.generate_copy`，ThreadPoolExecutor 并发，每平台 2~3 候选），`generate-progress` 供前端 2s 轮询；`rules.validate_candidate` 做字数硬校验（error 剔候选）+ 违禁词提示（warning 标黄）。
3. **审阅**：表格预览/编辑/重新生成/批准（`approve`）→ `approved`。
4. **发布**：`RunOptionsDialog` 展示 `quota`（按平台「已批准/今日已发/上限/剩余/将发布/将跳过」）→ `POST /api/batch/run` 启动 `scheduler` 串行限速发布，`status` 返回 summary + scheduler.alive；可 `stop`（当前条完成后终止）。
5. **产出**：`items/<id>/retry` 重试失败、`videos/csv` 导出清单、`report` 导出批次报告。

**风控**（`pipeline/scheduler.py`，`BatchScheduler(threading.Thread)`）：
- **跨「平台+账号」并发**（`max_concurrent` 默认 4，可 1~8），**同一「平台+账号」串行**（`_in_flight` 字典保证）；
- 条间间隔 `interval_min` 按「平台+账号」计（默认 5min，可 1~60）；
- 平台每日上限（douyin/kuaishou/tencent 5、xiaohongshu 3，未配置用 `daily_cap` 默认 25 兜底）→ 达限条目置 `skipped` 并写明原因，不空等；
- `sha256+platform+account` 防重发（`force` 可忽略）；定时时间已过 >2h 的条目跳过；
- `stop()` 结束所有在飞子进程（`kill_by_pid`），后续条目不再启动。

## 10. 已知缺陷清单（逐条读源码核对，附证据行号）

> 证据均来自当前工作副本；★ = 后果严重，建议优先修。
> 10.1~10.12 为后端/编排层，10.13 起为 Web 后端与前端。

### 10.1 ★ 批量「试跑」会污染防重发表 —— 最严重的一条

- `pipeline/scheduler.py:260-269`：退出码 0 时**无条件** `store.mark_published(...)` + 条目置 `success`，**完全不看 `self.dry_run / self.draft`**。
- 对比单发侧 `web/app.py:220-230` `_mark_published_from_task()`：明确 `if "--dry-run" in cmd or "--draft" in cmd: return`。
- 后果：勾选「试跑（填完不发布）」跑一次批量 → `published` 表被写入 → 之后真实发布全部被 `scheduler.py:146-152` 判为「该视频已在对应平台账号发布过(防重发)」→ 置 `skipped`，只能靠「忽略防重发」`force=True` 绕过。
- 本机数据库中 `published` 已有 20 行，需确认其中是否含试跑留下的脏记录。

### 10.2 ★ `dry_run` 对一半平台静默无效

- `planner.py:20-27` 只在 `PLATFORM_OPTS` 标了 `dry_run` 的平台追加 `--dry-run`：仅 **douyin / pdd / tmall / jd**。
- 对 **kuaishou / xiaohongshu / tencent / baijiahao** 传 `dry_run=True` **不会带上该参数 → 真实发布**；`draft` 同理仅 tencent 有效（`planner.py:72-75`）。
- UI 的「试跑」复选框（`RunOptionsDialog.vue:36`）对全部平台可见，无任何提示 → 用户在快手/小红书勾试跑会真的发出去（并叠加 10.1 被记入防重发）。
- 已核对 `--dry-run` 在 CLI（`mpau_cli.py:799/932/953/972`）与 uploader 侧（`douyin:1255`、`pdd:725`、`tmall:838`、`jd:769`）都有真实「填完不点发布」的实现，**与 `PLATFORM_OPTS` 的 4 个平台完全吻合**，所以问题纯粹是「能力表没覆盖」而非实现缺失。

### 10.3 ★ 崩溃后条目卡 `running`，且虚占当日额度

- `web/app.py:251-268 _restore_tasks()` **只恢复 `tasks`**（running/queued → interrupted）；`items` 停留在 `running` 的行**没有任何恢复逻辑**。
- `scheduler.py:136-137 _next_eligible()` 只取 `status == "approved"` → 孤儿 `running` **永远不会被重新调度**。
- 更糟：`scheduler.py:169-175 _check_daily_cap()` 把本批 `status in ("running","queued")` 的条目**计入今日已发** → 孤儿行虚占额度，导致后续条目被误判 `skipped`（"达到日上限"）。只能人工 `POST /api/batch/items/<id>/retry`。
- 附带：`"queued"` 对 items 是**死分支**（items 从不进入 queued）。

### 10.4 未到点的定时条目会让调度提前结束

- `scheduler.py:158-159`：未来定时的条目是 `continue`（跳过继续找），不是等待；若队列里只剩未来条目，主循环拿到 `None` 且无在飞 → `scheduler.py:84-92` 打印"没有可发布的条目, 调度结束"并 `break`。
- 后果：**定时条目被放弃**（仍留在 `approved`），需重新点「一键发布」；不存在"到点自动发"的常驻调度。

### 10.5 额度预览与实际风控不同源

- `batch_runner.py:447 quota_info()`：`cap = max(1, int(caps.get(platform) or 25))` —— **硬编码 25 兜底**，且 `published` 是**按平台聚合**（449-450）、同平台多账号会合并计数。
- `scheduler.py:163-176 _cap_for/_check_daily_cap`：兜底取 `self.daily_cap`，判定**按 (account, platform)**。
- 后果：自定义 `daily_cap ≠ 25`、或同平台多账号时，`RunOptionsDialog` 里"剩余 / 将发布 / 将跳过"会偏离实际执行结果。

### 10.6 CLI 与 Web 风控参数不同源

- `batch_runner.py:626-630`（`dispatch_batch` 的 `run` 分支）只传 `interval_min / dry_run / draft / force`，**不读 config.json** → `daily_cap` 用函数默认 25、`daily_caps=None`（平台上限全失效）、`max_concurrent` 用默认 4。
- 即同样一条视频，`mpau batch run` 与 Web「一键发布」的风控行为不一致。

### 10.7 AI 候选数硬编码 3，多账号多样性退化

- `copy_engine.py:44`（JSON schema 里写死 3 个候选对象）与 `:80`（prompt 里 `生成 {3} 个`）——`n_candidates` / `need` **只在下游 `_pick_candidates` 截断，不会让 LLM 多产**。
- `batch_runner.py:238-241` 按 `need = max(每平台条目数)` 要候选 → 同平台 ≥4 账号时取不满，退化为轮转（`scheduler` 上游的 `cands[idx % len]`）。
- `copy_engine.py:269-270` 的 `if len(accepted) < 2: pass` 是**空操作**（疑似丢失了"候选不足"告警逻辑）。

### 10.8 哈希只在首次登记时计算 → 同路径换文件会误判

- `batch_runner.py:38-43 / 67-70 / 100-102`：仅当 DB 中不存在该 path 时才调 `store.sha256_file`；已存在则直接复用旧行。
- 后果：**同名覆盖新视频**（剪辑师常见的"复用文件名"习惯）→ sha256 陈旧 → 防重发误判为已发布而跳过。
- 兜底：`scheduler.py:276-278 _fallback_hash` 在 sha 为空时用 `path:{path}` 当防重键。

### 10.9 `videos.status` 是死字段

- `store.py:55` 默认 `'new'`，全仓（grep `update_video`）**只有 goods_json/base_* 的写入，无 status 写入点**。

### 10.10 `plan_batch` 的 updated 分支是死代码

- `batch_runner.py:159-163`：`item_exists` 已按 account 精确匹配，`existing["account"] != item["account"]` 永不成立 → `updated` 恒为 0。

### 10.11 其它加固项（非功能性）

- `store.py:188 / 229 / 269`：`update_task/update_video/update_item` 用 **f-string 拼列名**——当前调用点均为内部白名单，但经 Web 传入的字段无过滤，属注入面；`items.status` / `tasks.status` **无 CHECK 约束**（自由字符串）。
- `store.py:104-107`：每操作独立连接，**无 WAL、无 busy_timeout、无连接池**（靠 `_write_lock` 串行写）。
- `rules.py:20-21`：`copy_rules.json` 在模块导入时读入 → **改规则必须重启进程**。
- `store.py:435 published_count_today` 用 `published_at LIKE 'YYYY-MM-DD%'` 全表扫描，且 `published` 无 `(account, published_at)` 索引。
- `pipeline/config.py:82-83`：**LLM Key / base_url 无任何环境变量可覆盖**，只能改 `config.json` 或走设置页。
- `web/app.py:840-860`：`/api/batch/run` 对 `interval_min`、`max_concurrent` 做了钳制，但 **`daily_cap` 未按 `min/max_daily_cap` 夹紧**（只做 `or` 兜底）。

### 10.12 ★ 批量任务日志在 UI 恒为空（代码 bug，已确定性验证）

- `web/app.py:271-276 _batch_task_created()`：把 scheduler 造的任务塞进内存 `_tasks` 时**显式** `t["log"] = []`。
- `web/app.py:681 api_tasks()`：`it["log"] = (lv.get("log") or [])[-MAX_LOG_LINES:]` —— **`or []` 的 fallback 对空 list 不生效**（`[]` 是 falsy，`or` 立刻返回右侧字面量）。
- 后果：批量任务在**服务未重启期间**点「日志」→ 空面板；scheduler 其实把日志写进了 SQLite（`scheduler.py:239 append_task_log`），但被内存空 list 覆盖掉。重启后 `_restore_tasks` 使 live 里没有该 id → 回退 DB → 日志又能看到。
- 验证：生产库 `b5-r0` 的 DB log 有 19 行；本次 API 返回 19 行是**因为服务在 15:53 重启过**（走回退分支）。代码路径本身必然为空（独立复现：情形 A「内存 log=[]」→ 返回 `[]`；情形 C「live 无该 id」→ 返回 DB 内容）。
- 影响面：**批量发布是最核心的链路**，失败时用户无法从 UI 看日志定位；`tasks.py` 里 `[VERIFY_REQUIRED]` / `[MANUAL_ACTION]` 标记匹配也因此对批量任务失效。
